Most calls inside an AI application are not requests for prose. They are decisions: which queue does this ticket go to, is this tool call safe to run, does this generated answer meet the rubric, which of four actions comes next. Teams have been making those decisions with a language model and a regular expression on its output, paying flagship prices for a yes or a no.

Microsoft Decision-1, announced on 9 October 2026, is Microsoft's answer to that waste: a model that scores a fixed set of options and returns a probability for each, without generating any text. This post explains what that means, how it differs from a large language model, what Microsoft claims and what is verified, and the use cases where it belongs. It is the companion to [Which LLM should you use?](/blog/which-llm-to-choose-2026/), where Decision-1 appears as one of nine model families, and it reuses the agent and evaluation patterns from my [Azure document-intelligence project](/portfolio/azure-ai-automation-document-intelligence/).

## The short answer

Decision-1 is a decision model, not a chatbot. Give it a text (the state) and a set of questions with fixed answers, and it returns a calibrated probability per answer in one pass: yes/no, one of several choices, or a position on an ordered scale. It is post-trained from Qwen3.5-9B, takes up to 32,768 tokens of text, costs $0.042 per million input tokens with free output, and runs in Microsoft Foundry and on OpenRouter. Use it for routing, classification, prioritisation, agent gates and grading. Use a language model when the answer has to be written.

| Fact | Value, as published by Microsoft |
| --- | --- |
| Announced | 9 October 2026, Microsoft Command Line blog; generally available in Microsoft Foundry |
| Base model | Qwen3.5-9B, post-trained for single-pass decision scoring; Microsoft says it will rebase on other models, including MAI and OpenAI |
| What it returns | A calibrated probability score for every supplied answer option; no text, no rationale |
| Question formats | Yes/no, multiple-choice, rating, classification and rubric-based questions |
| Input | Up to 32K tokens of text; no image, audio or video |
| Price | $0.042 per million input tokens; output tokens free |
| Where | Microsoft Foundry (sold directly by Azure, billed through the Azure subscription) and OpenRouter |
| Weights | Not distributed |

## What is the difference between a decision model and an LLM?

A language model generates an answer token by token; a decision model evaluates options you supply and scores them. The difference is the contract, not the intelligence. With an LLM you write "analyse this complaint and say what we should do", receive a paragraph, and parse it, hoping the format holds. With a decision model you send the complaint plus the options "refund, replace the order, escalate, do nothing", and receive a probability for each. Figure 1 shows the two flows on the same input.

<Figure src="decision-vs-llm.en.svg" caption="Figure 1. The same complaint through a language model and through a decision model. The LLM returns text you must parse; Decision-1 returns a probability per option you can threshold. The probabilities in the figure are illustrative, not measured." />

| Aspect | Large language model | Decision-1 |
| --- | --- | --- |
| Input | A prompt, free text, optionally images | A text state plus questions with fixed options |
| Output | Generated text, or JSON through structured outputs | A probability per option; a selected option for choice questions |
| Explanation | Can write a rationale | None by design |
| Latency | Seconds at the flagship tier; output length drives it | Milliseconds: one forward pass, no output tokens (Microsoft reports a median about 35 times lower than GPT-6 Sol) |
| Cost | $0.20 to $10 per million input tokens plus output | $0.042 per million input tokens, output free |
| Calibration | A "confidence: 0.8" in generated text is a guess | The probability is part of the API; Microsoft's target is that a 90 percent prediction is right about nine times in ten on representative cases |
| Best for | Writing, summarising, extracting, planning, coding | Classifying, routing, prioritising, verifying, grading |
| Failure mode | Hallucinated content, format drift | Mis-calibration on inputs unlike the benchmark; abstention or refusal available |

## How does the Decision-1 API work?

The request has three parts: the text to score, the questions, and the deployment name. Each question has a type, instructions and the allowed answers. Microsoft Learn documents three types in the Foundry Decisions API, and the Decision-1 catalogue entry lists the same shapes under different names: yes/no, multiple-choice and rating.

| Question type | Ask it to | Main result |
| --- | --- | --- |
| Predicate (yes/no) | Check whether a condition is true: "Does the customer ask for a refund?" | A probability from 0 to 1 that the condition is true |
| Choice (multiple-choice) | Select one option without an order: a department, a content category | The chosen value, a probability per option, and a separate confidence |
| Score (rating) | Rate an input against ordered levels: issue severity, answer quality | A probability per level and the probability-weighted average of the level indices |

This is the shape of a choice question and its answer in the Foundry Decisions API, as documented by Microsoft Learn on 21 October 2026. The values are illustrative, like Microsoft's own example.

```json
{
  "model": "YOUR-DEPLOYMENT-NAME",
  "input": "I was charged twice for my order.",
  "questions": [
    {
      "type": "choice",
      "name": "department",
      "instructions": "Which department should handle this complaint?",
      "choices": [
        { "value": "billing", "description": "Payments and refunds." },
        { "value": "technical", "description": "Product problems." },
        { "value": "shipping", "description": "Delivery and tracking." },
        { "value": "other", "description": "All other requests." }
      ]
    }
  ]
}
```

```json
{
  "type": "choice",
  "name": "department",
  "choice": "billing",
  "probabilities": [
    { "value": "billing", "probability": 0.95 },
    { "value": "technical", "probability": 0.02 },
    { "value": "shipping", "probability": 0.01 },
    { "value": "other", "probability": 0.02 }
  ],
  "confidence": 0.93
}
```

Four rules from the documentation that save a week of debugging:

1. **Give every question a unique name.** The answers array comes back in the same order, and the name is how you match them.
2. **Put independent questions in one request.** Several questions about the same text are one call; a question that depends on an earlier answer is a second call.
3. **Include a fallback option** such as "other" or "cannot tell" when the categories do not cover every input, and treat a refusal as different from a low probability.
4. **Choose each threshold on labelled examples** from your own application, based on the cost of a false positive and a false negative in that scenario.

The Microsoft Learn how-to for the Decisions API uses the gpt-6-luna model and the `/openai/v1/decisions` endpoint; Decision-1 is deployed from the Foundry catalogue as its own model with the same three question types. Check the catalogue entry for the exact endpoint of your deployment.

## When should you use Decision-1 instead of an LLM?

Ask one question: can you list every acceptable answer before the call? If yes, and you do not need a written explanation, a decision model fits. If the answer has to be written, summarised or explained, it does not.

| Problem | Language model | Decision-1 |
| --- | --- | --- |
| Write a customer email | Excellent | Not suitable |
| Explain a financial report | Excellent | Not suitable |
| Generate Python code | Excellent | Not suitable |
| Extract fields into your own JSON schema | Excellent, with structured outputs | Not suitable |
| Classify customer sentiment | Good | Excellent fit |
| Route a request to the right agent or department | Good | Excellent fit |
| Prioritise support tickets | Good | Excellent fit |
| Select the next action from a fixed list | Good | Excellent fit |
| Grade an AI-generated answer against a rubric | Good, with a rationale | Excellent fit for the score |
| Check whether a tool call is within policy | Good, slow | Excellent fit |
| Label a dataset with a fixed taxonomy | Good, expensive at volume | Excellent fit |
| Content filtering and safety screening | Good | Excellent fit |

The architectural takeaway is the same one that runs through the [LLM comparison](/blog/which-llm-to-choose-2026/): an agent might make thirty decisions during one run, and most of them do not need a reasoning model. A lightweight decision model handles the gates and the checks; the powerful model handles the planning and the writing.

## Where does a decision model sit in a real system?

Figure 2 shows the three places I put it: support triage, an agent loop, and an evaluation pipeline. Tap a layer to read what happens there.

<Stacks id="decision-flows" caption="Figure 2. Three places for a decision model. In support triage it labels every ticket and grades the drafted reply; in an agent loop it gates every tool call and checks every result; in evaluation it scores thousands of outputs against a rubric while a language model judge is sampled for the written rationale." />

The agent loop is the one that changes the economics most, so Figure 3 draws it in full.

<Figure src="decision-agent-loop.en.svg" caption="Figure 3. An agent loop with a decision model at the gate and at the check. The planner, a reasoning model, drafts each step; Decision-1 decides whether the tool call is within policy and needs approval, then whether the result means continue, retry or escalate." />

The pattern in words:

1. **Plan.** A reasoning model (Claude Opus 5.5, GPT-6 Sol) reads the task and drafts the next tool call.
2. **Gate.** Decision-1 answers three yes/no questions over the draft: within policy, a write action, needs human approval. Thresholds come from labelled examples; anything uncertain waits for a person.
3. **Act.** The tool call runs through the same registry that serves MCP clients, with permissions per role.
4. **Check.** Decision-1 scores the tool output with a choice question: continue, retry or escalate.
5. **Record.** The state goes to a checkpoint in PostgreSQL or Redis so the run can pause and resume, and every decision with its probabilities and cost lands in the OpenTelemetry trace.

This is the same approval-gated agent I built for the Azure document-intelligence project; the difference is that the gates were language-model calls then, and a decision model makes them cheaper and more consistent.

## What does it cost at scale?

Arithmetic at list price, not a quote. Three workloads, each with the assumptions stated, compared with the same tokens on GPT-6.1 Terra at $1 per million input tokens (output not counted, which flatters the LLM).

| Workload | Assumptions | Decision-1 per month | GPT-6.1 Terra input only, per month |
| --- | --- | --- | --- |
| Support triage | 10,000 tickets a day, 1,500 tokens each, 3 questions in one call | 450M tokens, about $19 | about $450 plus output |
| Agent gates and checks | 2,000 runs a day, 30 steps, 2 decisions a step, 2,000 tokens each | 7.2B tokens, about $302 | about $7,200 plus output |
| Evaluation | 100,000 answers graded a week, 3,000 tokens each | 1.2B tokens, about $50 | about $1,200 plus output |

The ratio is the point: at the same token count the decision model costs about 4 percent of a mid-tier language model's input price, and it produces no output tokens at all. Latency moves the same way, from seconds to milliseconds, which is what makes thirty gates per agent run acceptable.

## What are the limits?

- **No explanation.** The model returns probabilities and nothing else. When a user or an auditor needs a rationale, add a language-model call for the sampled cases.
- **Text only, 32K tokens.** No images, audio or video; long documents must be chunked or summarised first. For images, the Foundry Decisions API with gpt-6-luna offers the same question types.
- **Closed weights.** No download, fine-tuning, quantisation or self-hosting. If you need that, the base model Qwen3.5-9B is open, and a classifier trained on your labels remains the classic option.
- **Vendor benchmarks only.** Speed, accuracy and calibration figures are Microsoft's own as of 6 November 2026.
- **A moving base.** Microsoft plans to rebase Decision-1 on other models; keep the labelled set and rerun it on every version, as you would for any model retirement.
- **Not for consequential decisions about people.** The model card rules out sole reliance for credit, employment, housing, insurance, education, healthcare and legal rights.
- **Thresholds are yours.** A probability is only useful with a threshold you chose on your own data, and a low top probability means a person, not a coin flip.

## How do you set the thresholds?

1. **Collect 200 to 500 labelled examples** per question from real traffic, including the ugly ones.
2. **Run them through the question as written**, and store the probability per option.
3. **Plot precision and recall against the threshold** for each option, and pick the point where the cost of a false positive and a false negative balance for that scenario.
4. **Define the escalation band**: everything between the thresholds, plus refusals, goes to a person.
5. **Monitor drift weekly**: the share of escalations, the agreement with human labels on a sample, and the distribution of top probabilities. A shift means the inputs changed or the model version did.
6. **Rerun the set on every new version** of the model before switching the deployment.

## Which service should you choose for a decision?

Figure 4 is the three-question guide. It ends in Decision-1 more often than you would expect, and in a language model whenever the answer has to be written.

<Figure src="decision-guide.en.svg" caption="Figure 4. Decision model or language model. If you cannot list the answers, use an LLM with structured outputs; if you need a written explanation, use an LLM judge or combine it with Decision-1 for the score; if the input is not text or exceeds 32K tokens, use the Decisions API with gpt-6-luna or a multimodal model; otherwise Decision-1." />

| Need | First option | Why |
| --- | --- | --- |
| Fixed options, text, high volume | Microsoft Decision-1 | Calibrated probability, milliseconds, $0.042 per million |
| Fixed options over text and images | Decisions API with gpt-6-luna in Microsoft Foundry | Same predicate, choice and score questions, image input, language-model prices |
| Your own JSON schema or a written explanation | A language model with structured outputs (Responses API) | The answer has to be generated |
| Fixed options, must self-host | A classifier fine-tuned on your labels, or an open model such as Qwen3.5-9B with log-probability scoring | Weights you control; calibration is your job |
