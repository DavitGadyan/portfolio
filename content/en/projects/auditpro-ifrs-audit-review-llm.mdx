## The problem

An auditor opens a client's annual report and has to find what is wrong before anything else: a receivables figure in the notes that does not match the balance sheet, a cash-flow statement that does not end at the cash on the balance sheet, a retained-earnings roll-forward that does not tie, a lease or impairment disclosure that IFRS asks for and the report leaves out. Finding these by hand is slow, and it is the same work on every report. General chat models are not an answer: they invent numbers, they cite pages that do not hold the figure, and a client's unpublished financial statements cannot be sent to an outside API.

## What I built

**A first pass for the auditor, not a verdict.** You give Audit Pro a PDF, a link or pasted text. A small multi-agent pipeline returns two lists: **errors**, such as "the figure 48,138 on page 6 does not correspond with the page 2 value 50,876 for trade receivables", and **points of interest**, the places an auditor should test, each with the reason, the IFRS reference and a suggested procedure. Findings are drafts for an auditor to verify, and the prompts forbid asserting fraud.

**One fixed answer shape.** Every response, including failures, follows the same JSON Schema: company, statements found, reporting period and currency, then each error with its page and related pages, statement, line item, category, severity, expected and found figures, the IFRS reference (for example IAS 1.113), the quoted evidence, a confidence, which step detected it and whether it was verified. A partial result (one agent step failed) is marked 206, so a downstream tool or an audit file never receives a half answer that looks complete.

**The pipeline.**

1. **Ingest** reads the PDF page by page, a web page or pasted text, with page and size limits and an SSRF guard for links.
2. **A classifier agent** finds the company, currency, unit, period end and the statement type of every page.
3. **An extractor agent** turns each page into line items with values for the current and prior period. A value that is not printed on its cited page is dropped.
4. **Deterministic checks**, with exact decimal maths and no model: the accounting equation, totals against their components, gross profit and profit for the year, the cash-flow chain from sections to closing cash and the balance-sheet cash, the retained-earnings roll-forward, and the same figure on different pages. These produce the "page X does not correspond with page Y" findings.
5. **IFRS specialist agents run in parallel**, each on the pages routed to it: presentation and policies (IAS 1, 8), revenue and receivables (IFRS 15, 9), assets and impairment (IAS 16, 36, 38, IFRS 16), cash flow (IAS 7), and provisions, tax, related parties and events after the period (IAS 37, 12, 24, 10).
6. **Grounding and a critic.** A finding's quote must match the cited page, or it is dropped. A critic agent keeps or rejects each survivor and sets its confidence; anything below 0.5 becomes a point of interest instead of an error.
7. **Assemble**: remove duplicates, sort by severity, number the errors and validate the answer against the schema.

Every model call asks vLLM for schema-constrained JSON at temperature 0, and the prompt files are hashed into the answer's metadata, so each result says which model, revision and prompt version produced it.

## Choosing the model: 76 setups on one GPU

An audit firm runs this on its own hardware, so the question is which open model, quantization and serving setup gives the most trustworthy findings on one 24 GB card at an acceptable speed and cost. I built a benchmark lab to answer it with measurements.

**How a run works.** Each configuration is a pinned Hugging Face revision with exact vLLM arguments. The lab checks it fits the GPU, starts vLLM 0.34 on an RTX 4090 rented on Vast.ai ($0.415 an hour), then measures two things. Speed: AIPerf sends 4,000-token requests with 600-token answers straight to the engine at fixed concurrency and records time to first token, latency, tokens per second and peak VRAM. Quality: the full audit pipeline runs over synthetic IFRS reports. A generator builds consistent annual reports for invented companies, injects errors into the printed figures and keeps the exact answer for each one, so scoring needs no LLM judge.

**What is scored.** Recall (injected errors found), precision (findings that are real errors), numeric accuracy (both disagreeing figures right), page accuracy (the cited page really holds an error), grounding (quoted evidence is really on the page) and schema validity. The quality score is 30% recall, 20% precision, 20% numeric, 15% page and 15% grounding.

**The study.** 89 configurations were defined and 76 finished with full data: 19 open models in 27 checkpoints from 12 publishers (Qwen, DeepSeek, Meta, Microsoft, OpenAI, IBM, Liquid AI, AllenAI and community quantizers), 10 of them mixtures of experts, in 4-bit AWQ and GPTQ, FP8, MXFP4 and BF16, with and without an FP8 KV cache, with n-gram, suffix, EAGLE-3 and draft-model speculative decoding, and with CUDA graphs, chunked prefill, sequence caps, prefix caching and context lengths varied. Thirteen did not finish: the 32B models could not start in 24 GB, and the rest were lost to an early pipeline crash. These are the picks:

| Setup | Picked for | Quality | Recall | Per report | $ / 1,000 audits |
|---|---|---|---|---|---|
| Qwen3-14B FP8, FP8 KV cache | Production: best quality | 70.8 | 72.0% | 61 s | 1.83 |
| Qwen3-14B AWQ, suffix decoding | Fastest and cheapest at top quality | 68.6 | 69.3% | 24 s | 0.69 |
| Qwen3-14B AWQ, EAGLE-3 | Speed, same answers | 68.6 | 69.3% | 30 s | 0.88 |
| Phi-4 FP8 | Best arithmetic (88.3%) | 68.5 | 70.7% | 153 s | 4.53 |
| Qwen3-30B-A3B GPTQ (MoE) | Most errors found | 64.3 | 83.8% | 50 s | 1.57 |
| Qwen2.5-7B BF16, no prefix cache | Throughput (484 tokens/s) | 48.7 | 40.0% | 53 s | 1.56 |

Time per report is the average for one whole audit through the pipeline (several model calls, about 14,000 tokens), with four reports in progress at once. Cost is GPU rental only: $0.415 an hour over the evaluation's wall time, divided by the reports audited. Suffix decoding brings that to $0.69 per 1,000 audits; production pays $1.83 for FP8, the price of getting more figures right. Qwen2.5-7B reaches 484 tokens per second at 16 concurrent users in BF16 and 671 in 4-bit AWQ, but it finds too few errors for audit work (40% and 12%), so it counts only as a speed result.

**Under load.** The load curves show where one 24 GB card runs out. The 14B models flatten after about 8 concurrent requests: the production model goes from 213 to 216 tokens per second between 8 and 16, and its 95th-percentile time to first token climbs from 2.6 s at 4 to 35 s at 16 because requests queue for KV-cache memory (101,888 tokens fit at a 16k context); Phi-4 FP8 waits 39 s at 16. The 7B and 8B models keep scaling to 16: Qwen2.5-7B AWQ with an FP8 KV cache reaches 963 tokens per second, Llama 3.1 8B 528 and Qwen3-8B 500. For one auditor at a time a 14B model answers each call in about 8 s; a team of eight sharing the card is where a second GPU or a smaller KV cache starts to pay.

**Goodput, not peak throughput.** Every variant was swept closed-loop at 1 to 16 concurrent requests and once open-loop with Poisson arrivals, recording time to first token (TTFT), inter-token latency (ITL) and request time. Goodput counts only the calls that meet a latency SLO, here TTFT p95 under 2 s and ITL p50 under 50 ms. Under that SLO the production FP8 model serves 0.15 calls per second (2 concurrent requests), the Qwen3-14B AWQ build with suffix decoding 0.30 (4 concurrent), and Phi-4 FP8 0.24. Peak tokens per second would rank them differently: the 14B models reach 216 to 309 tokens per second at 16 users, but by then the first token takes 10 to 40 s.

**Goodput on the live production model.** An open-loop Poisson sweep against production (90 s per rate, same 4,000-in, 600-out requests, GPU and vLLM metrics sampled every second) shows the knee:

|---|---|---|---|---|---|---|---|
| 0.1 | 0.067 | 100% | 0.08 s | 31% | 0 | 0 s | 103 W |
| 0.2 | 0.133 | 100% | 1.1 s | 42% | 0 | 0 s | 155 W |
| 0.3 | 0.201 | 100% | 1.2 s | 72% | 0 | 0 s | 176 W |
| 0.4 | 0.260 | 90% | 2.0 s | 99% | 1 | 0.2 s | 195 W |
| 0.6 | 0.125 | 39% | 13.9 s | 100% | 14 | 4.9 s | 216 W |

Goodput peaks at about 0.26 requests per second; past it the KV cache fills, requests are preempted and queue, and goodput halves while raw throughput still rises a little. That is why capacity is planned on goodput, and why the API admits at most four audits at once, left of the knee. Decode stays memory-bound: memory-controller utilisation 45–81%, power at most 263 W of 450 W, no throttling. (GPU figures are nvidia-smi samples, not Nsight or DCGM profiling counters; achieved rates are below offered because requests still running at the 90 s cut-off are not counted.)

**OpenAI conformance.** Unit tests and an eight-check smoke test on production cover string and multi-part content, PDF file parts, the `chat.completion` object with `system_fingerprint` and usage, streaming chunks ending in `[DONE]` with an optional usage chunk, the OpenAI error envelope for 401, 400, 415 and 422, `/v1/models` and three concurrent audits. Not covered yet: cancelling the pipeline when a client disconnects, tool calls and reasoning content (it is a fixed audit task, not a general chat model), and sampling parameters, which are accepted but ignored. Speculative-decoding acceptance rates were not measured; the page reports only their end-to-end effect on real audits.

**What the techniques did.** Against plain Qwen3-14B AWQ, single runs on the same reports:

- **Suffix decoding was the biggest win.** It cut an audit from 44.0 s to 23.5 s (−47%, $0.69 per 1,000 audits); an EAGLE-3 head reached 29.9 s (−32%), a Qwen3-0.6B draft model 33.5 s (−24%) and n-gram 38.5 s at depth 4, 41.3 s at depth 2 and 46.4 s at depth 8, where drafting deeper stops helping. Every one returned the same findings on every paired report. In the random-token load test the same methods look 25–50% slower: audit pages repeat figures and labels a drafter can guess, random tokens do not. Speculative decoding has to be measured on real prompts.
- **4-bit has an accuracy cost.** Qwen3-14B AWQ finds as many errors as the FP8 build and is a third faster, but the paired A/B test rejected it on numeric accuracy: 21 points lower (95% CI −40 to −6). A throughput benchmark would never show that, and it is why production serves FP8.
- **FP8 KV cache plus n-gram** made each report 26% faster and 31% cheaper with the same recall, the best result before suffix decoding.
- **FP8 KV cache alone** gave 9–24% more throughput under load and room for more users, but did not shorten a single audit. On Phi-4 FP8 it gave 49% more throughput at 16 users and halved the queueing, with the same quality. On Qwen2.5-7B it broke the JSON output completely, so it is tested per model, never switched on by default.
- **CUDA graphs are not optional.** In eager mode an audit took 114 s, 2.6 times as long. Chunked prefill at 1,024 or 8,192 tokens, a cap of 64 sequences and an 8k, 16k or 32k context changed nothing measurable at this load.
- **Prefix caching** is worth keeping: the agents share long system prompts, and switching it off made audits 5% slower. A 32k context instead of 16k changed nothing measurable.
- **Who quantized the model matters as much as the bit width.** The GPTQ 4-bit build of Qwen3-30B-A3B found 84% of errors; four community AWQ 4-bit builds of the same family found 16% to 62%.
- **A mixture of experts is fast per call, not per audit.** Qwen3-30B-A3B activates about 3.4B of its 30.5B parameters per token, so one model call takes 4.0 s against 8.1 s for the dense 14B and throughput is about 1.7 times higher, but it writes more per report, so a whole audit takes longer. Its grounding score, under 25% like DeepSeek-R1's and Phi-4's, looks like a measurement issue that is still to be investigated.
- **The GPU is memory-bound.** On the 8B model the lab measured 947 GB/s of memory bandwidth, which caps decoding at about 155 tokens per second for 6.1 GB of weights; the engine reached 113, or 73% of that ceiling.

**What the A/B tests said.** The framework ran 53 paired comparisons with Holm correction and a 2-point non-inferiority margin. It rejected five: Qwen3-14B AWQ against FP8 on numeric accuracy, and four community AWQ builds of Qwen3-30B-A3B whose whole recall confidence interval sat below the margin (for example −70 points, from −86 to −51). The other 48 were inconclusive: every speculative-decoding and engine variant gave identical answers, which changes speed, not findings, and with 15 to 30 documents per run smaller quality differences cannot be proven. None was accepted, and the page says so instead of declaring winners. Speed itself varies 1.7% in tokens per second and 9% in 95th-percentile first-token time between runs on the same host, so the next step is adaptive A/B testing on the target hardware: interleaved runs on one GPU, at least three performance replicates, sequential stopping and successive halving across variants.

**Honest limits.** The quality gates I set for production (numeric accuracy 98%, page accuracy 95%, grounding 95%, recall 85%, schema validity 99%) are not met by any configuration yet, so these are the best results so far, not a certified model. The scores come from synthetic English reports (15 or 30 documents per run), not an accountant-reviewed golden set, and most rows are single runs. A new champion replaces the old one only when it wins by at least 2 points.

## In production

The firm now serves Qwen3-14B FP8 with an FP8 KV cache: the highest quality score (70.8, recall 72%, numeric accuracy 70%) and the figures the AWQ build gets wrong. vLLM loads it offline from a SHA-256-verified model store behind the audit API, which speaks the OpenAI chat-completions format: `POST /v1/chat/completions` with the report as text or as a base64 PDF file part returns the audit JSON as the message content, with streaming, a usage block, OpenAI-style errors and `GET /v1/models`. Qwen3-14B AWQ and Phi-4 FP8 sit on disk as fallbacks, a one-minute switch.

In the production smoke test a seven-page synthetic PDF for an invented company, Tavush Timber LLC, took 54.6 s and 13,617 tokens across the pipeline's model calls; the same report as text took 52.4 s, and three PDFs sent at once all finished within 56.2 s. It found all four injected errors on the right pages: retained earnings that do not tie between pages 5 and 2, with both exact figures; the current-assets total, with the right printed figure but a wrong expected one; the unbalanced balance sheet, blaming total assets instead of total equity and liabilities; and a cash-basis revenue policy against IFRS 15, reported three times. Six findings for four real issues, plus one point of interest (profit before tax down from 72,740 to 10,089): detection is strong and the figures are the weak spot, the same picture as the benchmark.

The API also runs on a public demo endpoint on the rented RTX 4090 (access on request). Twelve new synthetic annual reports, held out from every benchmark set, went through it from a laptop over the internet, four at a time: 12 of 12 succeeded with schema-valid answers in 58.6 s per audit (56.1 to 61.8 s), about 245 audits an hour on one card and 13,500 tokens per audit. They found 74% of the planted errors (31 of 42), 70% of the 83 findings were real, and 64% of the figures were exact, in line with the offline benchmark for this model (recall 72%, numeric accuracy 70%): the deployed system reproduces the measured quality.

## One report, start to finish

![A page of the synthetic input report and Qwen3-14B AWQ's result on it](/images/portfolio/auditpro-example.jpg)

The input is a synthetic annual report for an invented company, Syunik Mining Services OJSC, with four injected errors: total current assets printed as 127,899 instead of 122,644 (page 2), gross profit 74,809 instead of 70,879 (page 3), total equity and liabilities 288,604 instead of 270,552, so the balance sheet does not balance (page 2), and an accounting policy that says property, plant and equipment is not depreciated, against IAS 16.43 (page 6). Qwen3-14B AWQ with a 32k context, the quality pick before the 8k run, read the seven pages in 42.8 seconds and returned valid JSON with five findings. It found all four errors, put four findings on the right page and gave the exact expected and found figures for two of the three arithmetic errors. Two of its five findings were not real errors, so precision on this report was 60%, below the 90% acceptance bar. Across the 15 reports the same model found every error in six, nothing in three, and passed the acceptance bar on one: the reason every finding stays a draft for the auditor.

## The lab

The Next.js app is where the model is chosen and served.

- **Lab**: pick models, engines and techniques. Several selected launch a test job; one selected deploys it. A capacity planner shows the free VRAM, the weights, the KV cache and how many users fit before anything starts.
- **Experiments**: every run, the quality gates it passed or failed, a quality-against-cost chart with the Pareto frontier, and a recommendation per profile (quality, balanced, throughput, cost).
- **A/B decisions**: a candidate against its baseline with replicates, bootstrap confidence intervals and Holm-corrected p-values, ending in accept, reject, no benefit or inconclusive.
- **Optimization**: speculative decoding acceptance, prefix caching and tenant isolation, chunked prefill, KV cache capacity, the roofline and a batching simulator.
- **Audit a report**: upload a report and read the errors and points of interest.
- **Live**: GPU and inference tiles, with Grafana dashboards for vLLM, the GPU and audit quality behind them.

## Deployment and security

One container image holds vLLM, the API, the dashboard, Prometheus and Grafana for a single GPU server; a Helm chart runs them as separate pods with network policies, non-root containers, read-only file systems and KEDA autoscaling. Model weights are downloaded once to a volume, checked against Hugging Face's SHA-256 hashes, and the engine then runs offline. GitHub Actions builds the images, signs them by digest with cosign, scans them, and packages and signs the Helm chart. 251 tests (154 for the API and pipeline, 97 for scoring, selection and the lab) run without a GPU against a stand-in engine; on 40 synthetic reports the deterministic checks find every error they target, and on 20 clean reports they report nothing.

The API needs a key on every audit and metrics route; the dashboard uses basic auth and keeps the key on the server. Request bodies and prompts are never logged, every answer is validated against the schema before it is returned, and the deploy controller only accepts allow-listed, digest-pinned, signed images. Benchmarks on rented marketplace GPUs use synthetic reports only; real client documents run on the firm's own hardware.

## What is next

An accountant-reviewed golden set to replace the synthetic one, adaptive A/B testing with repeated performance runs, suffix decoding on the FP8 production model, OCR for scanned PDFs, Armenian and Russian reports, and per-user access with client-level isolation.
