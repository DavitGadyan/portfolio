La pregunta detrás de este artículo es una línea de oferta de empleo: implementar y optimizar soluciones de servicio de modelos con frameworks como vLLM, TensorRT-LLM, SGLang o Triton Inference Server. La trampa es tratar esos cuatro nombres como competidores. No son el mismo tipo de cosa, y las herramientas de Kubernetes que los rodean (Helm, llm-d) son otra capa más.

Lo escribí como la referencia que tengo abierta al dimensionar una pila de servicio. Separa las capas, compara las herramientas en tablas, dice cuándo encaja cada una y termina con cómo llm-d, Helm y Kubernetes ejecutan pools separados de prefill y decode. Si quieres empezar por la elección del modelo, lee [¿Qué LLM usar?](/es/blog/which-llm-to-choose-2026/).

## La respuesta corta

Usa **vLLM** salvo que una restricción apunte a otro lado: es la opción general con más soporte de hardware y de modelos. Elige **TensorRT-LLM** para despliegues solo NVIDIA donde la velocidad máxima justifique la configuración extra, **SGLang** cuando muchas peticiones comparten prefijos largos, y **Triton** cuando un servidor debe dar frente a varios modelos o pipelines. Añade **llm-d** cuando un pod de motor ya no basta y necesitas enrutado, conciencia del prefix cache y pools separados de prefill y decode en Kubernetes.

Todo lo de abajo se comprobó el 19 de noviembre de 2026 contra la documentación de los propios proyectos (en Fuentes). Donde una celda dice "no confirmado", no encontré la afirmación en la página que leí, que no es lo mismo que "no existe". No hago afirmaciones de rendimiento: la velocidad depende del modelo, la GPU, la precisión y el tráfico.

## ¿Qué es cada herramienta y en qué capa está?

| Herramienta | Capa | Qué hace |
| --- | --- | --- |
| vLLM | Motor | Ejecuta el modelo con PagedAttention, continuous batching, prefix caching y un servidor de API compatible con OpenAI |
| TensorRT-LLM | Motor | Biblioteca de código abierto de NVIDIA para inferencia optimizada de LLM en GPU NVIDIA, con una API Python y arquitectura basada en PyTorch |
| SGLang | Motor | Framework de servicio de alto rendimiento para modelos de lenguaje y multimodales, con RadixAttention, prefix caching y paralelismo multi-GPU |
| Triton Inference Server | Capa de servicio | Servidor de código abierto que despliega modelos de varios frameworks tras HTTP/REST y gRPC, con dynamic batching, ensembles y métricas |
| llm-d | Orquestación | Pila de inferencia de código abierto para Kubernetes que ejecuta motores como vLLM y SGLang en un clúster; proyecto CNCF Sandbox |
| Helm | Despliegue | Instala y configura aplicaciones de Kubernetes a partir de charts y un archivo de valores |

## ¿Cómo se comparan vLLM, TensorRT-LLM, SGLang y Triton?

| Característica | vLLM | TensorRT-LLM | SGLang | Triton |
| --- | --- | --- | --- | --- |
| Batching | Continuous batching, chunked prefill | In-flight batching, chunked prefill | No confirmado en las páginas que leí | Dynamic batching por modelo; in-flight batching con el backend de TensorRT-LLM |
| KV cache | PagedAttention, prefix caching | Paged KV cache con reutilización de bloques | RadixAttention, prefix caching | Delegado al backend |
| Cuantización | FP8, MXFP8/MXFP4, NVFP4, INT8, INT4, GPTQ/AWQ, GGUF | FP8 en H100 y posteriores, FP4 en B200 | No confirmado | Delegado al backend |
| Decodificación especulativa | n-gram, suffix, EAGLE, DFlash | EAGLE, MTP, n-gram | No confirmado | A través del backend |
| Paralelismo | Tensor, pipeline, datos, expertos, contexto | Tensor, pipeline, expertos | Paralelismo multi-GPU | Delegado al backend |
| Hardware | GPU NVIDIA y AMD, CPU x86, ARM, PowerPC | GPU NVIDIA | NVIDIA, AMD, Intel Xeon, Google TPU, Ascend NPU y otros | GPU NVIDIA, CPU x86 y ARM, AWS Inferentia |
| API | Compatible con OpenAI, Anthropic Messages, gRPC | API Python; CLI de servicio | Compatible con OpenAI | HTTP/REST y gRPC (protocolo KServe) |
| Prefill/decode desagregado | Sí | Beta | No confirmado | No aplica |

## ¿Cuándo tiene más sentido cada una?

| Situación | Elige | Por qué |
| --- | --- | --- |
| Modelo de pesos abiertos, primer despliegue, hardware mixto | vLLM | Mayor cobertura de hardware y modelos, endpoint sencillo estilo OpenAI |
| Flota solo NVIDIA, importan latencia y coste por token | TensorRT-LLM | Kernels afinados por NVIDIA y FP8/FP4 en GPU recientes |
| Agentes o chat con prompts de sistema largos compartidos | SGLang, o vLLM con prefix caching | Reutilizar el prefijo evita recalcular los mismos tokens; prueba ambos |
| Un endpoint para varios modelos, ML clásico y LLM | Triton | Repositorio de modelos, ensembles, métricas, varios backends |
| Muchas GPU en varios nodos, enrutado consciente del KV | llm-d sobre el motor | El enrutado y la gestión de pools no son trabajo del motor |
| Experimento en portátil o solo CPU | vLLM para CPU, o un runtime local | vLLM indica soporte de CPU; producción va en GPU |

## ¿Qué optimizaciones importan y qué cuestan?

| Técnica | Qué mejora | Contrapartida |
| --- | --- | --- |
| Continuous o in-flight batching | Uso de la GPU: las peticiones nuevas se unen a un batch en marcha | Un batch mayor sube la latencia por petición |
| Paged KV cache | Menos memoria desperdiciada, más peticiones concurrentes | Sobrecoste de gestionar bloques |
| Prefix caching | Se salta el prefill de prefijos compartidos, baja el tiempo hasta el primer token | Solo ayuda si los prefijos se repiten de verdad |
| Cuantización (FP8, INT4, FP4) | Pesos más pequeños, más sitio para el KV cache | Hay que comprobar la calidad en tu tarea |
| Decodificación especulativa | Menos pasos secuenciales de decode | Necesita un método de borrador; la ganancia varía con el prompt |
| Paralelismo tensor, pipeline, expertos | Cabe un modelo mayor que una GPU | Exige enlaces rápidos, ver NVLink e InfiniBand |
| Desagregación prefill/decode | Escalado y ajuste separados por fase | Coste de transferir el KV, más piezas móviles |

## ¿Qué añade llm-d en Kubernetes y cómo encaja Helm?

Piénsalo como cuatro trabajos. Kubernetes gestiona el clúster. Helm instala y configura aplicaciones en él. llm-d aporta enrutado y orquestación conscientes de la inferencia. vLLM (o SGLang) ejecuta el modelo.

| Pieza | Trabajo | Cómo llega |
| --- | --- | --- |
| Gateway | Punto de entrada de las peticiones | Helm, o un gateway existente |
| Router y endpoint picker (EPP) | Elige el pod de motor para cada petición | Helm |
| Pods de motor (vLLM) | Generan tokens | Manifiestos de Kubernetes o Kustomize en las guías actuales de llm-d |
| LeaderWorkerSet | Agrupa pods para réplicas de modelo multinodo | Helm |
| Monitorización | Métricas y paneles | Herramientas adicionales |

llm-d describe sus despliegues como "well-lit paths", recetas probadas que incluyen charts de Helm o manifiestos de Kustomize, parámetros de ajuste, cargas de ejemplo, benchmarks y monitorización. Los caminos de su documentación incluyen una base optimizada, enrutado por latencia predicha, enrutado preciso consciente del prefix cache, una caché de prefijos por niveles, compartición de prefix cache entre pares, desagregación prefill/decode y paralelismo de expertos amplio para modelos de mezcla de expertos.

Una instalación con Helm, con la ubicación del chart tomada de la receta publicada del router de llm-d (confírmala con la guía actual, porque los charts cambian):

```bash
helm install my-router \
  oci://ghcr.io/llm-d/charts/llm-d-router-standalone \
  -f router-values.yaml \
  --namespace llm-d \
  --create-namespace
```

Helm renderiza las plantillas del chart con tus valores como recursos de Kubernetes y los envía a la API; los controladores de Kubernetes concilian entonces el clúster con ese estado deseado. Para cambiar la configuración editas el archivo de valores y ejecutas `helm upgrade` con el mismo nombre de release. Este esquema es solo ilustrativo, no son las claves exactas de los charts actuales de llm-d:

```yaml
router:
  replicas: 2
prefill:
  replicas: 4
decode:
  replicas: 8
```

Subir decode de 8 a 12 pide entonces cuatro pods más a Kubernetes, siempre que la carga respete ese ajuste y el clúster tenga las GPU.

## ¿Deben prefill y decode correr en nodos separados?

Prefill lee todo el prompt en paralelo y está limitado por cómputo; decode produce tokens de uno en uno y lo limitan el ancho de banda de memoria y la capacidad del KV cache. Los pools separados permiten dar a cada fase sus propias GPU, paralelismo y señal de escalado, y evitan que los prompts largos frenen el decode. El precio es mover el KV cache entre pools, por lo que la red (NVLink dentro del nodo, InfiniBand o RoCE entre nodos) decide si compensa.

| Opción | Tiene sentido cuando | Cuidado con |
| --- | --- | --- |
| Prefill y decode combinados, un pool | Modelos pequeños o medianos, prompts cortos, fase inicial | Los prompts largos retrasan el decode de otros usuarios |
| Enrutado consciente del prefix cache, pods combinados | Chat de varios turnos, prompts de sistema compartidos | Pods saturados si el router ignora la carga |
| Pools de prefill y decode desagregados | Alta concurrencia, prompts largos, objetivos de latencia estrictos | La transferencia del KV exige una red rápida |
| Paralelismo de expertos amplio | Modelos grandes de mezcla de expertos en muchas GPU | Fuerte exigencia de interconexión y operación |

Para un mensaje de seguimiento en el mismo chat, el pod que ya tiene el KV cache de la conversación ahorra cálculo, así que un router que sabe dónde están los prefijos en caché supera al round-robin. Es el mismo razonamiento que mantener capacidad de prefill separada: controlas el espacio de caché y el escalado por fase.

## ¿llm-d solo admite unos pocos modelos?

No. El soporte de modelos viene del motor. La documentación de modelos admitidos de vLLM lista más de 200 arquitecturas de Hugging Face (Llama, Qwen, DeepSeek, Mistral, Gemma, Phi, Nemotron y modelos multimodales). Lo que cambia es el nivel de validación.

| Pregunta | Qué comprobar |
| --- | --- |
| ¿Puede el motor ejecutar el modelo? | La arquitectura aparece en los modelos admitidos de vLLM |
| ¿Funciona en mi hardware? | CUDA, ROCm u otro backend, más el formato de cuantización |
| ¿Funcionan juntos el paralelismo y el tipo de KV cache? | Paralelismo tensor, pipeline, datos o expertos y el dtype de la caché |
| ¿Tiene llm-d una receta? | Existe un well-lit path o un camino específico del modelo para tu configuración |
| ¿Está validada la receta? | Algunas recetas se marcan como mantenidas por la comunidad en lugar de validadas cada noche |

## ¿Qué hacer primero?

1. Despliega un modelo con vLLM y un endpoint compatible con OpenAI; registra el tiempo hasta el primer token, los tokens por segundo y el uso del KV cache con tus prompts reales.
2. Prueba la cuantización y el prefix caching, y conserva un conjunto de prompts de referencia para comprobar la calidad.
3. Prueba TensorRT-LLM y SGLang con los mismos prompts si tu hardware y tu tráfico lo justifican.
4. Contenedoriza, mete el motor en un release de Helm y añade un pool de nodos GPU con el device plugin de NVIDIA.
5. Solo entonces añade llm-d, enrutado consciente del prefijo y, si las cifras lo piden, pools separados de prefill y decode.
